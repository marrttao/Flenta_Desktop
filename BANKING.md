# Банківська пісочниця

Гілка Desktop `MarisBanking` додає сторінки `/` і `/banking` для API з гілки
Backend `MarisBanking` (також сумісна з `MarisCombined`). Це тестовий банкінг:
картки, поповнення та перекази не працюють із реальними грошима.

Інтерфейс містить звичайну HTML-розмітку та робочі форми для тестування API.
Дизайн і CSS не додаються: оформлення підготують дизайнери.

## Запуск

1. Запустіть Backend з налаштованими Supabase Auth і PostgreSQL та застосованими EF-міграціями.
2. У Desktop виконайте `npm ci` і `npm run dev -- --host 127.0.0.1`.
3. Відкрийте `http://127.0.0.1:5173/banking` і увійдіть у свій обліковий запис.

API за замовчуванням: `http://127.0.0.1:5080`. Іншу адресу можна задати через
`VITE_API_BASE_URL` у `.env.local`. У Backend дозвольте точну адресу фронтенда в CORS.
Ключі Supabase і підключення PostgreSQL зберігаються лише на стороні Backend.

Backend потребує `Supabase__Enabled`, `Supabase__Url`, `Supabase__PublishableKey`,
`Supabase__FrontendUrl`, а також `Banking__Enabled=true`, `Banking__ConnectionString`
і постійний `Banking__CardEncryptionKey` (32 випадкових байти у Base64).
Після зміни конфігурації перезапустіть Backend. Не змінюйте ключ шифрування,
якщо потрібно читати реквізити раніше випущених карток.

## Ручна перевірка

1. Відкрийте два рахунки кнопкою «Відкрити рахунок».
2. Оберіть перший рахунок і поповніть його на 1000 ₴.
3. Створіть картку. Перевірте її блокування й розблокування.
4. Відкрийте реквізити та підтвердьте свій пароль. Реквізити приховуються після
   закриття вікна або через 60 секунд; вони не записуються в localStorage чи журнал.
5. Переказ між своїми рахунками: 100 ₴ з першого на другий. Спочатку натисніть
   «Розрахувати переказ», перевірте комісію та суму, потім підтвердьте.
6. Перевірте баланси 900 ₴ і 100 ₴ та новий запис в історії.
7. Спробуйте переказ за IBAN другого рахунку. Комісія і повна сума списання
   приходять із Backend; UI не розраховує їх самостійно.
8. Для переказу іншому користувачу скопіюйте його ID рахунку або IBAN з його
   кабінету. Одержувач повинен існувати в тій самій банківській пісочниці.
9. Перевірте відмову при недостатньому балансі, сумі 0 або більше двох знаків
   після коми, переказі на той самий рахунок та неправильному паролі реквізитів.
10. Закрийте тестову картку; повторна активація недоступна. Рахунок залишається.

Після помилки мережі повтор ідентичного поповнення/переказу використовує той
самий `Idempotency-Key`. Після отриманої відповіді наступна дія отримує новий ключ.
Ключ утримується тільки в пам’яті поточної сторінки, тому при невідомому результаті
спершу оновіть історію кнопкою «Оновити», не перезавантажуючи сторінку.

Сесія авторизації, як і в гілці `MarisAuth`, зберігається в пам’яті вкладки.
Після перезавантаження сторінки потрібно увійти знову.

## Перевірки коду

```sh
npm run lint
npm test
npm run build
```

Тести перевіряють точність сум, повтор запиту після втрати відповіді, зміну
одержувача/суми та нові ключі після виконаної або відхиленої операції.
